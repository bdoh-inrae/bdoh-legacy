# Envoi des fiches vers Theia/OZCAR

État : en cours, commencé le 2026-10-27 ; suit l'administration (`dev/plans/2026-10-26_administration.md`). Point 7 du portage dans `ROADMAP.md`.

But : le format pivot d'un observatoire (sa fiche, ses jeux de données et leurs chroniques, au format JSON de Theia/OZCAR), son contrôle par le schéma de Theia et son envoi, servis par le nouveau BDOH à l'identique de l'ancien.

## Ce que ça couvre

Relevé dans l'ancien code (`../bdoh/src/Irstea/`) :

- **`BdohTheiaOzcarBundle`** : 20 classes du format pivot (`Model/`), le `Mapper` qui les remplit depuis un observatoire (347 lignes), la sérialisation en JSON (`SerializerJSON`, par JMS Serializer 1.14), le contrôle par le schéma (`SchemaJSON`, opis/json-schema 1.1), la mise en zip (`ZipJSON`) et l'envoi (`EnvoiJSON`, Guzzle 6, `PUT` vers `<uri_theia_send_data><code>/new/BDOH.zip`, authentifié par le code Theia et le mot de passe déchiffré de l'observatoire). Deux commandes : `theia:send:json:data` (l'envoi, lancé par la file `json_theia`) et `theia:dump:pivot` (le format pivot de tous les observatoires, sur la sortie).
- **Pages**, dans `ObservatoireController` de la consultation, déjà portées avec le module 2 mais sans leurs services : télécharger le JSON (`…/observatoire/{id}/downloadJson`), le contrôler (`…/jsonValidator`, gabarit `JsonValidator/report.html.twig`), l'envoyer (`…/envoieJson`, qui met la tâche en file), et `…/save` (mise à jour automatique, dont le formulaire est en commentaire et qu'aucune tâche ne mène).
- **Chargement du schéma** : `BdohConsultBundle/Service/JsonSchema/` (`HttpLoader`, `CachingLoader` sur APCu par Doctrine Cache, `SpyingLoader`), déjà copiés, pas encore branchés.
- Le mot de passe Theia, chiffré par `PasswordEncryptionService`, est porté depuis le module 6.

Les courriels, que la feuille de route rangeait aussi au point 7, sont tous portés avec leurs modules (comptes, demandes d'accès, exports) ; ce qui reste est la configuration de production (`dev/plans/2026-10-26_deployment.md`).

## Choix

- **Sérialisation à nous, sans JMS Serializer.** Les classes du format pivot n'ont aucune annotation : JMS 1.14 y écrit toutes les propriétés, dans l'ordre de leur déclaration, sans les valeurs nulles (ni dans les tableaux), un objet vide en `{}`, et passe le tout à `json_encode` sans option. Une trentaine de lignes refont cela ; JMS 3 en demanderait quatre paquets et changerait ses réglages par défaut (`JSON_PRESERVE_ZERO_FRACTION`). La comparaison des JSON le vérifie.
- **opis/json-schema 1.1**, celle de l'ancien, si elle tourne sous PHP 8.4 : la page du contrôle montre ses erreurs telles quelles (`keyword`, `dataPointer`, `keywordArgs`, `totalErrors`), que la version 2 présente autrement. Le cache du schéma passe de Doctrine Cache (retiré) au cache de Symfony.
- **Guzzle 7**, successeur de la 6 avec la même interface et les mêmes messages d'erreur, que la sortie de la tâche recopie.

## Comparaison

`compare.py theia`, l'ancien code sur PostgreSQL 17 et le nouveau, chacun sur sa copie de la base, au nom d'un administrateur :

1. Le JSON téléchargé de chaque observatoire qui a un code Theia, comparé comme un objet.
2. La page du contrôle de chacun, avec une copie du schéma de Theia servie par chaque instance (pas d'accès à l'extérieur), hors dépôt (`../bdoh_reference/theia/`).
3. L'envoi : un mot de passe Theia d'essai enregistré par le formulaire de l'observatoire, la tâche menée par la file, reçue par un récepteur de développement (`dev/compare/theia-receiver.php`, servi le temps de la comparaison) qui garde la méthode, l'adresse, l'en-tête d'authentification (son empreinte) et le contenu du zip ; puis un envoi refusé (401) ; la sortie et l'état des tâches, et `miseajourautomatique`.

## Étapes

1. Paquets (Guzzle 7, opis/json-schema 1.1) ; classes du format pivot, `Mapper`, services, commandes ; chargement du schéma.
2. `compare.py theia`, jusqu'à l'identité.
3. Le décalage des coordonnées (ci-dessous), corrigé à part, comparé.
4. Relecture par un second Claude.

## Relevé en route

- **Coordonnées décalées.** Les requêtes du point d'une chronique et de l'emprise d'un jeu de données (`ChroniqueRepository::getPoint`, `DataSetRepository::getReclangleEnglobant`) passent par `ST_Transform(…, 4236)`, le système « Hu Tzu Shan 1950 » (Taïwan), et non 4326 (WGS 84, celui de GeoJSON) : les coordonnées envoyées à Theia sont décalées de 300 à 700 m selon les stations (mesure du 27 octobre sur la base de production). À corriger après l'identité, et à signaler aux gestionnaires : les fiches déjà publiées portent ce décalage.
