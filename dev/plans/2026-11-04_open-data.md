# Ouvrir les données

État : en cours, proposition validée par Lou le 2026-11-04 ; écrite et fusionnée dans `main`, comparée sur les nouveaux dumps, ses écarts au registre et ses 10 fautes vues. Reste : le navigateur (`dev/plans/2026-11-04_validation.md`). Point « Ouvrir les données » de `ROADMAP.md`. Ce qui est décidé, et pourquoi, est dans `dev/decisions.md` (« Ouverture des données ») : ce fichier ne dit que comment le faire.

## Quand

Après la preuve d'identité avec l'ancien, comparé à part, avant les essais : les testeurs et les gestionnaires voient l'ouverture elle-même et donnent leur aval, derrière le VPN et un mot de passe d'accès (`dev/plans/2026-10-26_deployment.md`).

## Ce qui change

**1. La règle** (`BdohRightVoter::canDownload`). Une chronique visible se télécharge sans compte ; une chronique cachée demande les droits d'aujourd'hui, inchangés. Une demande qui mêle les deux répond 403 sans le droit, comme aujourd'hui.

**2. L'export sans compte.** Aujourd'hui, le formulaire met une tâche en file (`JobManager::enqueueExport`, qui demande un `Utilisateur`), et le résultat part en pièce jointe d'un courriel (`AbstractExportCommand`, `--send-to`). Sans compte, il n'y a pas d'adresse. Proposition :

- Le formulaire reste le même : dates, type, pas, format, fuseau. Les fichiers exportés ne changent pas (mêmes formats).
- L'export passe toujours par la file : une grosse chronique dépasse le délai d'une page (`volumes.py` dira de combien), et la file protège le serveur, une tâche à la fois.
- Le fichier va dans `var/exports/`, sous un jeton impossible à deviner. Une page dit où en est la tâche, puis donne le lien, valable quelques jours ; une tâche de nettoyage retire les fichiers échus.
- Avec un compte, le lien part aussi par courriel, et plus jamais de pièce jointe de plusieurs Go.
- Au-dessus d'un certain nombre de mesures (d'après `nbmesures`, sur la période demandée), un compte est nécessaire, et le lien arrive par courriel (objectif de Lou du 3 novembre).
- Une limite de fréquence par adresse IP, comme pour les liens de connexion (`config/packages/rate_limiter.yaml`).

**3. Les conditions d'utilisation.** La case à cocher du formulaire (`termsOfUses`) cède la place à la Licence Ouverte Etalab pour une chronique visible, avec un rappel de citer la source : BDOH et le DOI du jeu de données, quand il y en a un. Une chronique cachée garde la case et ses conditions. Les fichiers de licence du zip : `dev/decisions.md`.

**4. Les pages.** Les boutons de téléchargement suivent le droit (`is_granted('DOWNLOAD', …)`, déjà dans les gabarits) : ils apparaissent d'eux-mêmes. La demande d'accès (`BesoinController`) reste, pour les données fermées, et son texte le dit. Le visualiseur ne change pas. Les exports de station et de jeu de données, déjà coupés dans l'ancien (`{% if false and …`), restent coupés.

**5. Ce que le code permet déjà, relevé le 2026-11-04 :**

- Les commandes d'export savent écrire dans un fichier (`--write-to`, `AbstractExportCommand::createArchiver`) : `enqueueExport` n'a qu'à recevoir un chemin au lieu d'un compte. La file `job_queue_export` les mène déjà une à la fois, en priorité basse, après les recalculs.
- L'historique accepte un export sans auteur en base (`historique.auteur_id` peut être vide), mais `BdohLogger::createHistoriqueDonneesExport` demande un `Utilisateur` : à assouplir, ce qui garde le compte des exports.
- Les pages de suivi (`/jobs/`, `/jobs/{id}`) sont pour les comptes. Un anonyme suit sa tâche par une page à part, portée par son jeton.

**6. La fiche Theia.** Elle envoie la contrainte d'accès de chaque jeu de données (`accessUseConstraint`) : les 28 jeux de la production valent « Conditions Generales Utilisation (voir pdf) ». À remplacer dans l'administration, sans code, et les fiches changent à leur prochain envoi : « Licence Ouverte 2.0 » pour 26 jeux, « Licence Ouverte 2.0, sauf chroniques en accès restreint » pour les 2 qui ont des chroniques cachées (Arc-Isère, Observatoire des Sédiments du Rhône). De même, à la prochaine mise à jour des 20 DOI, ce qu'ils déclarent de leur licence, chez leur registre, hors de BDOH.

## Comment on le vérifie

- `compare.py` : les seuls écarts avec l'ancien sont les boutons et le formulaire, à inscrire au registre.
- Cas « nouveau seul » : sans compte, une chronique visible se télécharge, et le fichier est le même qu'avec un compte ; une chronique cachée répond 403 pour un anonyme, pour un compte sans droit, et dans une demande mêlée ; elle se télécharge avec un droit sur elle, ou avec le rôle sur l'observatoire ; un jeton inconnu ou échu répond 404 ; le seuil et la limite de fréquence se déclenchent.
- Une entrée dans `dev/differences.md`, et une relecture par un second Claude de tout chemin qui sert des valeurs.
- Pour les gestionnaires : la liste de leurs chroniques, ouvertes et fermées, par observatoire, à comparer à ce qu'ils attendent.

## Les choix de Lou (2026-11-04)

1. **Le seuil au-dessus duquel un compte est demandé.** Une chronique seule n'y tombe jamais ; c'est un ensemble de chroniques trop lourd qui le demande. Mesuré sur la plus grosse chronique (2,4 millions de mesures, `volumes.py`) : 43 s et 336 Mo à l'identique, 422 s en moyenne horaire. Une page ne tiendrait pas, la file si. Nombre retenu pour commencer : 5 millions de mesures par demande, à revoir après les essais, soit au pire une quinzaine de minutes de file. Le panier de chroniques, plus tard, suivra la même règle.
2. **La durée du lien** : 7 jours.
3. **Les points de contrôle des chroniques visibles s'ouvrent aussi.** Ils n'ont pas de case à eux : ils appartiennent à une chronique (`pointcontrole.chronique_id`) et suivent son `estvisible`. `canConsultCheckpoints` regardera donc la chronique, comme `canConsultTimeseries`, et un cas vérifie que ceux d'une chronique cachée restent fermés.

## Suivi

- 2026-11-04, relecture par un second Claude, code seulement, avant tout essai. À traiter :
  - Le lien d'une archive ne contrôlait plus rien si une chronique liée avait été supprimée (`fileAction`).
  - Un archivage raté donnait une tâche « finie » et un lien mort : `ZipArchiver::close` n'est pas contrôlé.
  - Rien ne bornait le disque ni la file sans compte. Les fichiers temporaires restés ne sont pas purgés. Un lien dure plus de 7 jours si aucun export ne tourne.
  - Une tâche relancée réutilise le même jeton, et peut retirer l'archive d'une autre.
  - `--send-to` sans `--jms-job-id`, une réponse d'export sans referer, un identifiant trop long.
  - Outil : `EXPORT_LINK` ne lit pas le CRLF d'un courriel ; le texte d'aide est sur toutes les pages ; le formulaire des comptes n'est plus comparé ; un arrêt dans `open_data_checks` perd le rapport de `state` ; le chemin de l'archive se voit dans `/jobs` ; le cas des points de contrôle peut réussir à vide ; une archive de chronique cachée reste sur le disque.
  - Textes : l'accueil, l'inscription, la demande d'accès disent encore qu'il faut un compte pour télécharger.
  - L'archive d'une chronique visible contenait encore les conditions d'utilisation : réglé, voir ci-dessous.
- 2026-11-04, licences : décision écrite dans `dev/decisions.md` ; 20 Go de place pour les archives, qui remplacent la garde sur l'espace disque. Oracle : ses conditions propres ne vivent que sur l'ancien serveur, son fichier local de 77 octets vient de `compare.py`. S'il manque, le zip d'une chronique cachée prend celles de BDOH.
- 2026-11-04, relecture traitée sur la branche ; pas encore essayé. Le lien d'une archive se juge d'après les arguments de la tâche, plus d'après ses entités liées. Un archivage raté fait échouer la tâche. Sans compte, 30 tâches en attente et 2 Go libres au moins. Un lien échu se refuse à la lecture, sans attendre la purge. Une relance a son propre jeton. Les cas tournent sur une copie à eux, écrivent leurs résultats au fil de l'eau, et retirent les archives à la fin.
- 2026-11-04, premier essai, sur la base réduite et les anciens dumps : tous les cas d'ouverture de `state` passent. Il a montré un écart, corrigé : un export en échec sortait sur le code 255 au lieu de 1. Le comparateur et les fautes de l'ouverture n'ont pas encore tourné dans `mutants.py`.
